# ITDeskService: Glossary (พจนานุกรมคำศัพท์ในโปรเจกต์)

เอกสารนี้รวบรวมคำศัพท์ (Terminology) และความหมายที่ใช้สื่อสารกันภายในระบบ ITDeskService เพื่อให้ทีมพัฒนา ผู้ใช้งาน และเจ้าหน้าที่ทุกฝ่ายมีความเข้าใจตรงกัน

## 1. คำศัพท์ทั่วไปเกี่ยวกับระบบ (General Terms)
- **Ticket (ทิคเก็ต) / Case (เคส):** ใบงานแจ้งซ่อมหรือใบแจ้งปัญหาที่ถูกสร้างขึ้นในระบบ แต่ละใบจะมี **Ticket ID** ที่ไม่ซ้ำกัน โดยใช้รูปแบบ Running Number รายเดือน (เช่น `IT-202609-0001`) และจะมี **PCAR ID** (`PCAR-YYYYMM-XXXX`) แยกต่างหากเฉพาะสำหรับเคสที่มีการเปิด Task 2
- **User / Requester:** ผู้ใช้งานทั่วไป หรือพนักงานในบริษัทที่เป็นผู้แจ้งปัญหาเข้ามาในระบบ
- **Dashboard:** แผงควบคุมหรือหน้าจอสรุปผล
  - *User Dashboard:* หน้าจอที่ผู้ใช้งานทั่วไปใช้เพื่อดูสถานะเคสของตัวเองเท่านั้น (Data Isolation)
  - *Admin/Helpdesk Dashboard:* หน้าจอมอนิเตอร์สำหรับทีม IT เพื่อดูภาพรวม สถิติ KPI และรายการเคสทั้งหมดในระบบ โดยมีการจัดกลุ่มสถานะใหม่ ได้แก่ "ดำเนินการแก้ไข" (In Progress) และ "ทดสอบและส่งมอบ / รอยืนยัน" (Testing & Delivery) รวมไปถึงการกรองมาตรการป้องกัน

## 2. โครงสร้างทีม IT (IT Roles & Tiers - มาตรฐานสากล ITIL 4)
ระบบได้ปรับโครงสร้างบทบาทผู้ใช้งานสู่ 5 บทบาทหลักระดับสากล (5 Core Roles) เพื่อความยืดหยุ่นและการขยายตัวสู่ Commercial-Ready:
- **1. System Administrator (`administrator`):** ผู้ดูแลระบบสูงสุด มีสิทธิ์เข้าถึง ควบคุม และตั้งค่าโครงสร้างระบบทั้งหมด (จัดการบริษัท, ผู้ใช้, ทีมงาน, Audit Logs, สำรองข้อมูล, ตั้งค่าระบบ)
- **2. IT Service Manager (Tier 3) (`manager`):** ผู้จัดการฝ่ายบริการไอที / หัวหน้าทีม มีหน้าที่กำกับดูแลทีมงานเฉพาะทาง ติดตามภาระงานของช่าง (Technician Workload) ผ่านความสัมพันธ์ของทีมที่ดูแล (`teams.manager_id`), ส่งต่อหรือมอบหมายงานใหม่ (Re-assign/Re-escalate), ตรวจสอบความถูกต้องของการซ่อม (Audit), และอนุมัติมาตรการป้องกันปัญหา (Task 2)
- **3. Technical Specialist (Tier 2) (`technician`):** ช่างเทคนิคผู้เชี่ยวชาญเฉพาะทาง ผู้ปฏิบัติงานแก้ไขปัญหาที่ซับซ้อน โดยสังกัดทีมเฉพาะทางต่างๆ ผ่านตารางความสัมพันธ์ `team_user` (เช่น ทีม Hardware, Network, Software, DevOps, Infrastructure) มีสิทธิ์กดเริ่มสืบสภาพ (Analyzing), บันทึกสาเหตุรากเหง้า (Root Cause), บันทึกการแก้ไข (Resolution Notes), ส่งมอบงาน (Resolved), และจัดทำมาตรการป้องกัน (Task 2 PCAR)
- **4. Service Desk Agent (Tier 1) (`helpdesk`):** เจ้าหน้าที่รับเรื่องด่านหน้า (First Contact Resolution) ผู้มีหน้าที่รับเรื่อง ตรวจสอบข้อมูล คัดกรอง (Triage), ประเมินความเร่งด่วน (Priority), แก้ไขปัญหาเบื้องต้น และส่งต่อเคสไปยังทีมช่างเฉพาะทาง พร้อมสิทธิ์ในการดูแลจัดการข้อมูลผู้ใช้งานทั่วไป (Normal Users)
- **5. End User / Requester (`user`):** พนักงานหรือผู้ใช้งานทั่วไปในบริษัท ผู้แจ้งปัญหาหรือคำร้องขอรับบริการไอที ติดตามสถานะเคสของตนเอง สื่อสารผ่านคอมเมนต์ และกดยืนยันรับงานพร้อมให้คะแนนความพึงพอใจ (CSAT)

*(หมายเหตุ: ระบบมี Migration และ Logic รองรับบทบาทเดิมแบบ Backward Compatibility: `manager_software`, `manager_network_hardware` ถูกปรับรวมเข้าสู่ `manager` พร้อมเชื่อมโยง `teams.manager_id` และ `team_hardware`, `team_network`, `team_software` ถูกปรับเป็น `technician` พร้อมผูกสังกัดทีมใน `team_user` โดยอัตโนมัติ)*

## 3. ขั้นตอนและการจัดการใบงาน (Workflow & Operations)
- **Triage (การคัดกรอง):** กระบวนการที่ Helpdesk ตรวจสอบใบแจ้งซ่อมและประเมินว่าปัญหาคืออะไร กระทบส่วนไหน
- **Priority (ความเร่งด่วน):** ระดับความสำคัญของปัญหา ซึ่งส่งผลต่อระยะเวลา SLA (เช่น ทั่วไป, ปานกลาง, สูง, ด่วนที่สุด)
- **Assign (การมอบหมาย):** การส่งมอบเคสให้ช่างหรือเจ้าหน้าที่รับไปดูแล
- **Escalate / Forward (การส่งต่อ/ยกระดับ):** การส่งเคสต่อให้ผู้เชี่ยวชาญในระดับที่สูงกว่า (เช่น จาก Helpdesk ส่งให้ Tier 2) ระบบจะเปลี่ยนสถานะเคสเป็น **Assigned (มอบหมายแล้ว/รอรับงาน)** เพื่อรอช่างกดรับงาน
- **SLA (Service Level Agreement):** ข้อตกลงระดับการให้บริการ หรือ "ระยะเวลามาตรฐาน" ที่ต้องใช้ในการแก้ไขปัญหา หากแก้ไม่เสร็จตามเวลาจะถือว่า **Overdue (เกินกำหนด)**
- **SLA Overdue Warning Alert:** ระบบตรวจจับและส่งการแจ้งเตือนอัตโนมัติล่วงหน้าผ่าน Email, Database และ Log Line Notify เมื่อเคสใกล้หมดเวลา SLA (Warning - ตามค่าที่ตั้งไว้ เช่น เหลือน้อยกว่า 60 นาที) หรือเมื่อเคสเกินกำหนดเวลาแล้ว (Breached) โดยทำงานผ่าน Scheduled Command `sla:check-warnings` ทุก 1 นาที
- **SLA Met / Breached:** สถานะสรุปเมื่อช่างทำการส่งมอบงาน (Handover) ว่าสามารถส่งมอบได้เสร็จสิ้นทันตามกรอบเวลา SLA (SLA Met) หรือส่งมอบเกินเวลามาตรฐาน (SLA Breached)
- **First Contact Resolution (FCR):** การที่ Helpdesk สามารถแก้ไขปัญหาให้จบและปิดงานได้ทันทีตั้งแต่รับเรื่องครั้งแรก โดยไม่ต้องส่งต่อให้ช่าง

## 4. กระบวนการซ่อมและการปิดงาน (Resolution & Closing)
- **Root Cause (สาเหตุรากเหง้า):** สาเหตุที่แท้จริงที่ทำให้เกิดปัญหาขึ้น (ในขั้นตอนการสืบสภาพ เมื่อกรอกสาเหตุรากเหง้าแล้วบันทึก ระบบจะถือว่าการสืบสภาพสิ้นสุด และขยับสถานะเข้าสู่ In Progress ทันที)
- **Resolution Notes:** บันทึกการแก้ไขปัญหาเฉพาะหน้า รายละเอียดขั้นตอนและวิธีการที่ช่างใช้ในการแก้ไขปัญหาเบื้องต้น สามารถบันทึกเก็บไว้ได้ตลอดเวลาระหว่างดำเนินการซ่อม
- **Handover (การส่งมอบงาน):** การที่ช่างหรือเจ้าหน้าที่กดปุ่มส่งมอบงานให้ผู้แจ้งหลังจากนำงานไปส่งมอบหรือประสานงานกับผู้แจ้งเรียบร้อยแล้วจริง ๆ เพื่อเปลี่ยนสถานะเป็น **รอผู้แจ้งกดรับงาน (Resolved)** และหยุดการนับเวลา SLA ทันที
- **Acceptance (การรับทราบการแก้ไข):** การที่ผู้แจ้งปัญหาเข้ามากดปุ่มยืนยันรับทราบการแก้ไขและให้คะแนนความพึงพอใจ CSAT เพื่อเปลี่ยนสถานะเป็น ปิดใบงาน (Closed) ทันที (หากผู้แจ้งไม่กด Helpdesk จะกดแทนได้หลังผ่านไป 5 นาที)
- **Cancelled (ยกเลิก):** สถานะของเคสที่ถูกยกเลิก โดยสามารถถูกยกเลิกได้จาก ผู้แจ้ง, Helpdesk, หรือ Manager ซึ่งเคสที่ถูกยกเลิกจะไม่นำไปคำนวณใน KPI

## 5. การวิเคราะห์และป้องกัน (Analysis & Prevention - Task 2)
- **Task 2 (Preventive Action):** ขั้นตอนหลังจากแก้ไขปัญหาเฉพาะหน้าแล้ว เป็นการระบุข้อมูลวิเคราะห์รากเหง้าของปัญหาและสร้างมาตรการป้องกัน
- **Why Why Analysis (การวิเคราะห์ด้วยเทคนิคทำไม-ทำไม):** เครื่องมือในการสืบสวนปัญหาระดับ Tier 2 โดยการถาม "ทำไม" ซ้ำๆ (3-5 ครั้ง) จนกว่าจะพบสาเหตุรากเหง้า (Root Cause)
- **Post-Mortem:** การประชุมหรือสรุปบทเรียนหลังจากเคสถูกปิดแล้ว เพื่อหาทางป้องกันไม่ให้เกิดซ้ำ
- **Preventive Measure (Specific/Systemic):** มาตรการป้องกันที่แบ่งออกเป็น "เฉพาะกรณี" (หน้างาน) และ "ทั้งระบบ" (ปรับปรุงกระบวนการหรือนโยบาย)
- **P-CAR Form 4:** รูปแบบรายงานสำหรับพิมพ์ (Printable Report) ของใบบันทึกเคส ที่แสดงข้อมูลสรุปตั้งแต่เริ่มเปิดเคส, เวลาสืบสภาพ, รายละเอียดอาการ, การอนุมัติซ่อม ไปจนถึงมาตรการป้องกัน
- **PCAR ID:** เลขที่เอกสาร P-CAR ที่จะถูกสร้างขึ้นอัตโนมัติเฉพาะตอนที่ช่างเริ่มดำเนินการสืบสภาพ (Task 2) แยกขาดจาก Ticket ID เพื่อให้เลขเอกสารรันต่อเนื่องกันเฉพาะเคสที่เปิด PCAR จริงๆ
- **PCAR Cancellation & Reason (การยกเลิก P-CAR และการระบุเหตุผล):** กระบวนการที่หัวหน้า (Manager - Tier 3) เปลี่ยนใจเลือก "ไม่ต้องการมาตรการป้องกัน" ในเคสที่มีเลข PCAR แล้ว ระบบจะบังคับให้ระบุเหตุผลการยกเลิก (`pcar_cancellation_reason`), ปรับสถานะ Task 2 เป็น `cancelled` และเก็บประวัติผู้ยกเลิก (`pcar_cancelled_by`) และเวลาที่ยกเลิก (`pcar_cancelled_at`) เพื่อเป็น Audit Trail
- **PCAR Re-activation (การนำเลข PCAR เดิมกลับมาใช้งานต่อ):** กระบวนการที่หัวหน้า (Manager - Tier 3) สลับใจกลับมาเลือก "ต้องการมาตรการป้องกัน" อีกครั้งในเคสที่เคยถูกยกเลิกไปแล้ว โดยระบบจะนำเลข `pcar_no` เดิมกลับมาใช้งานต่อทันที ปรับสถานะ Task 2 กลับเป็น `in_progress` ปลดลายน้ำยกเลิกออก และบันทึกประวัติการสลับคำตัดสินลงใน Comments ของใบงาน โดยไม่ต้องรันเลข PCAR ใหม่ข้ามเดือน
- **P-CAR Cancelled Watermark (ลายน้ำตรายางยกเลิก P-CAR):** ลายน้ำกราฟิกตรายางสีแดงกึ่งโปร่งใส (Red Stamp Overlay) เอียง 25 องศา วางกึ่งกลางหน้ารายงาน P-CAR Form 4 (`print.blade.php`) แสดงข้อความ *"⚠️ P-CAR ถูกยกเลิก / CANCELLED"* พร้อมระบุเหตุผล ผู้ยกเลิก และวันเวลาที่ยกเลิก โดยออกแบบเป็น Absolute Overlay ที่ไม่กระทบต่อสัดส่วนตารางและคงการพิมพ์ได้พอดี 1 หน้ากระดาษ Legal
- **P-CAR:** หลักการหรือหมวดหมู่ที่ใช้จัดกลุ่ม "สาเหตุของปัญหา" ประกอบด้วย:
  1. **Man (คน):** พฤติกรรม, ความรู้, การทำตามมาตรฐาน
  2. **Machine (เครื่องจักร):** อุปกรณ์, สเปคคอมพิวเตอร์, การตั้งค่า
  3. **Material (วัสดุ):** อะไหล่, ของสิ้นเปลือง, หมึกพิมพ์
  4. **Method (วิธีการ):** ขั้นตอนการทำงาน, คู่มือระบบ
  5. **Environment (สิ่งแวดล้อม):** อุณหภูมิ, ความชื้น, สถานที่ทำงาน

## 6. คำศัพท์อื่นๆ (Miscellaneous)
- **Email Verification:** การยืนยันตัวตนผ่านอีเมล โดยผู้ใช้ที่สมัครสมาชิกใหม่ต้องคลิกลิงก์ที่ระบบส่งไปให้ในอีเมลก่อนจึงจะเข้าใช้งานระบบได้ เพื่อป้องกันการใช้อีเมลปลอม แต่หากเป็นบัญชีที่ Administrator หรือ Manager เป็นผู้สร้างให้เอง (หรือนำเข้าผ่านไฟล์ CSV) ระบบจะกำหนดสถานะยืนยันแล้วอัตโนมัติ (Bypass) เพื่อให้สามารถเข้าใช้งานได้ทันที พร้อมมีฟังก์ชันตรวจสอบการตั้งค่า Email (SMTP Test Connection) ให้ผู้ดูแลระบบทดสอบการส่งอีเมลจริงได้ทันที
- **Smart Delete (Account Deactivation):** ระบบลบผู้ใช้งานแบบมีเงื่อนไข หากเป็นบัญชีใหม่ที่ไม่มีประวัติจะลบถาวร (Hard Delete) เพื่อลดขยะสะสม แต่หากมีประวัติแล้วจะเปลี่ยนเป็นการระงับบัญชี (Inactive) แทนเพื่อรักษาความสมบูรณ์ของข้อมูลใบงาน พร้อมระบบเก็บเวลาเข้าสู่ระบบล่าสุด (Last Login)
- **Separation of Duties (การแบ่งแยกหน้าที่เพื่อป้องกันผลประโยชน์ทับซ้อน):** หลักการควบคุมภายในด้านไอทีที่ไม่อนุญาตให้ทีมงานผู้ให้บริการหรือผู้ดูแลระบบ (Roles: `technician`, `helpdesk`, `manager`, `administrator`) เป็นผู้เปิดเคสแจ้งซ่อมเอง เพื่อป้องกันไม่ให้เกิดกรณีเปิดเคสเอง รับงานเอง ปิดงานเอง หรือบิดเบือนสถิติ KPI โดยสงวนสิทธิ์การเปิดเคสแจ้งซ่อมให้เฉพาะผู้ใช้งานทั่วไป (End User: `user`) เท่านั้น
- **5W2H:** หลักการพื้นฐานในการอธิบายและแจ้งปัญหาให้ครบถ้วน ประกอบด้วย Who (ใคร), What (เกิดอะไรขึ้น), Where (ที่ไหน), When (เมื่อไหร่), Why (ทำไม), How (ทำอย่างไร), และ How much/many (ความถี่/จำนวนเท่าไหร่)
- **CSAT (Customer Satisfaction Score):** ระบบประเมินความพึงพอใจของผู้แจ้งปัญหา (1-5 ดาว) หลังจากผลการแก้ไขได้รับการอนุมัติ (Phase 1)
- **Quick Templates:** ปุ่มลัดอาการเสียยอดฮิตในหน้าแจ้งซ่อม เพื่อช่วยให้ผู้ใช้กรอกหัวข้อและรายละเอียด (5W2H) ได้รวดเร็วขึ้น (Phase 2)
- **Empty State:** หน้าจอว่างเปล่าแบบมินิมอลที่จะแสดงเมื่อผู้ใช้ยังไม่มีข้อมูลใบแจ้งซ่อม เพื่อเพิ่มความน่าใช้งาน (Phase 2)
- **Mobile-First UI:** การออกแบบหน้าจอ (โดยเฉพาะหน้า Dashboard) ให้รองรับการใช้งานบนมือถือเป็นหลัก โดยแปลงตารางข้อมูล (Data Table) ให้กลายเป็นการ์ด (Cards) เพื่อความสะดวกในการอ่านและกดผ่านจอมือถือ
- **Dynamic Company Management:** ระบบการดึงข้อมูลบริษัทของพนักงานจากฐานข้อมูลแทนการฝังค่า (Hardcode) เพื่อรองรับการขยายตัวขององค์กรหรือบริษัทในเครือ
- **LINE OA Webhook:** ระบบรับคำสั่งอัตโนมัติผ่านแชท LINE Official Account (เช่น รับคำสั่ง "แจ้งซ่อม" หรือ "เช็คสถานะ" และดำเนินการเปิดเคสหรือดึงข้อมูลให้ทันที)
- **Reply Message (LINE):** การส่งข้อความตอบกลับผู้ใช้งานผ่าน LINE ฟรี 100% โดยมีเงื่อนไขว่าต้องตอบกลับภายใน 1 นาทีหลังจากผู้ใช้งานพิมพ์เข้ามา (ใช้ Token ที่ได้มาตอบกลับ 1 ครั้ง)
- **Push Message (LINE):** การที่ระบบเป็นฝ่ายส่งข้อความแจ้งเตือนไปหาผู้ใช้ใน LINE ก่อน (โดยที่ผู้ใช้ไม่ได้พิมพ์เข้ามา) ซึ่งมีโควต้าจำกัดรายเดือน (ฟรี 200 ข้อความ/เดือน)
- **Date Format:** รูปแบบการแสดงผลวันที่มาตรฐานในระบบทั้งหมด (ยกเว้นในช่องอินพุตประเภทวันที่) กำหนดให้ใช้รูปแบบ `dd/MMMM/yyyy` (เช่น `10 มกราคม 2026`) หรือตรงกับฟอร์แมต `d F Y` ในภาษา PHP
- **Administrator:** ผู้ดูแลระบบสูงสุด มีสิทธิ์ในการเข้าถึงและตั้งค่าระบบทั้งหมด (เช่น จัดการรายชื่อบริษัท, ระงับผู้ใช้งาน, ดู Audit Log) โดยระบบจะไม่อนุญาตให้แก้ไขชื่อของตัวเองเพื่อป้องกันข้อผิดพลาด
- **Audit Log:** ระบบเก็บบันทึกประวัติการกระทำอัตโนมัติ (เช่น สร้าง, แก้ไข, ลบข้อมูล) โดยเฉพาะของ Administrator เพื่อใช้ตรวจสอบความเคลื่อนไหว (Traceability)
- **Data Retention (Audit Logs):** การตั้งค่าระยะเวลาจัดเก็บข้อมูลประวัติย้อนหลัง เช่น 1 ปี 3 ปี 5 ปี โดยระบบจะมีสคริปต์อัตโนมัติ (Purge) ทำการลบข้อมูลที่เก่ากว่ากำหนดทิ้งเพื่อประหยัดพื้นที่ฐานข้อมูล
- **Impersonation:** ระบบการจำลองสิทธิ์เป็นผู้ใช้คนอื่น (สำหรับ Administrator เท่านั้น) เพื่อให้ Admin สามารถล็อกอินในมุมมองของ User คนนั้นเพื่อตรวจสอบปัญหาที่ได้รับแจ้งได้ โดยจะมีป้าย (Banner) แจ้งเตือนสีแดงค้างไว้บนหน้าจอเพื่อกันความสับสน และระบบจะไม่ทำการบันทึกเวลาเข้าสู่ระบบล่าสุด (`last_login_at`) เพื่อป้องกันข้อมูลการใช้งานจริงของพนักงานคลาดเคลื่อน
- **Force Password Reset:** ฟังก์ชันที่อนุญาตให้ผู้ดูแลระบบสั่งส่งอีเมลเปลี่ยนรหัสผ่าน (Password Reset Link) ไปยังผู้ใช้งานโดยตรง ในกรณีที่ผู้ใช้ลืมรหัสผ่าน
- **CloudPanel:** ระบบ Web Hosting Control Panel ที่ใช้จัดการเซิร์ฟเวอร์ (Deployment) ของระบบ ITDeskService
- **CSV Import/Export:** ระบบสำหรับนำเข้าและส่งออกข้อมูล (เช่น รายชื่อพนักงาน, รายชื่อบริษัท) ในรูปแบบไฟล์ตาราง เพื่อรองรับการจัดการข้อมูลจำนวนมาก (Bulk Operations)
- **Automated Backup:** ระบบสำรองข้อมูลฐานข้อมูลและไฟล์แนบรูปภาพทั้งหมดแบบอัตโนมัติ (ผ่าน Laravel Task Scheduler และ Spatie Backup) โดยกำหนดค่าให้รันทุกวันเวลาเที่ยงคืน เพื่อป้องกันข้อมูลสูญหาย
- **Manual Restore:** การกู้คืนข้อมูลจากไฟล์ Backup (.zip) โดยแอดมินจะต้องทำการแตกไฟล์และนำไป Import กลับด้วยตัวเอง (ผ่าน phpMyAdmin และ File Manager) เพื่อความปลอดภัยและความเสถียรของเซิร์ฟเวอร์
- **Holidays Management:** ระบบการตั้งค่าวันหยุดนักขัตฤกษ์สำหรับใช้ประกอบการคำนวณระยะเวลา SLA และเวลาทำการขององค์กร โดยมีนโยบายป้องกันการลบวันหยุดในอดีต (Past Holidays Protection) เพื่อไม่ให้กระทบต่อผลการคำนวณ SLA ย้อนหลัง
- **Favicon & Branding:** ไอคอนและชื่อประจำเว็บไซต์ที่ปรากฏบนแท็บของ Web Browser โดยระบบใช้ชื่อ `ITDeskService` และใช้สัญลักษณ์ลูกบาศก์ Polymate IT Solutions เป็นไอคอน
- **React & Inertia.js (Hybrid Architecture):** การพัฒนาสถาปัตยกรรมส่วนหน้า (Frontend) โดยย้ายจาก Blade Views เดิมไปเป็น React Components ร่วมกับ Inertia.js เพื่อมอบประสบการณ์แบบ Single Page Application (SPA) ที่รวดเร็ว ลื่นไหล โดยยังคงใช้ Laravel Routing และ Backend เดิมได้อย่างกลมกลืน
- **SMTP Test Connection:** ฟังก์ชันการทดสอบการเชื่อมต่อเซิร์ฟเวอร์ส่งอีเมลแบบ Real-time บนหน้าจอการตั้งค่าระบบ (Settings) ช่วยให้ Administrator ส่งอีเมลทดสอบจริงไปยังอีเมลปลายทางเพื่อตรวจยืนยันความถูกต้องของ Host, Port, Username, Password และ Encryption ก่อนบันทึกการตั้งค่าใช้งานจริง
- **Dynamic Company-Department Mapping:** ระบบเชื่อมโยงและกรองตัวเลือกแผนก (Department) ตามบริษัท (Company) ที่ผู้ใช้งานเลือกแบบเรียลไทม์ ป้องกันปัญหาการเลือกแผนกข้ามบริษัทที่ไม่สอดคล้องกัน
- **Inertia Location Redirect (`Inertia::location`):** กลไกการทำ Full Browser Redirect (HTTP 409) จากฝั่ง Inertia.js เมื่อต้องการนำทางข้ามไปยังหน้าเดิมที่เป็น Blade View (เช่น การสลับสิทธิ์ผ่าน Impersonation หรือการออกจากโหมดจำลองสิทธิ์) เพื่อป้องกันไม่ให้ Inertia นำ HTML Response ไปเปิดเป็น Modal Iframe ซ้อนทับบนหน้าเดิม
- **Backup Notifications Management:** ระบบบริหารการแจ้งเตือนการสำรองข้อมูล โดยปิด Notification ในการกด Backup ผ่านหน้าเว็บ (`--disable-notifications`) เพื่อให้การทำงานรวดเร็วและป้องกันข้อผิดพลาด SMTP 550 ส่วนรอบอัปเดตอัตโนมัติรายวันจะส่งต่อเมื่อมีการระบุ `BACKUP_NOTIFICATION_EMAIL` ใน `.env` เท่านั้น
- **Live Auto-polling (Inertia):** กลไกการดึงข้อมูลอัปเดตบนหน้าแดชบอร์ดแบบเรียลไทม์ (ทุก 15 วินาที) โดยใช้ `router.reload({ only: ['cases', 'stats'] })` ของ Inertia.js ช่วยให้ผู้ใช้เห็นสถานะล่าสุดของใบงานและตัวเลข KPI ทันทีโดยไม่ต้องโหลดหน้าเว็บใหม่ทั้งหมด และรักษาระดับการเลื่อนหน้าจอ (Scroll Position) ไว้อย่างราบรื่น
- **Thai Typography & Metric Normalization:** การกำหนดแบบอักษรภาษาไทยมาตรฐานด้วย Google Fonts (`Prompt` และ `Noto Sans Thai`) ผ่าน Bunny Fonts และการกำหนด `leading-normal` พร้อมปรับความสูงของ Input/Select ให้สมดุล (`h-12 py-2.5 px-4`) เพื่อป้องกันปัญหาสระบน/ล่างและวรรณยุกต์ (เช่น ุ, ู, ้, ่) หลุดหรือถูกตัดขอบบนระบบปฏิบัติการ Windows และอุปกรณ์พกพา
- **Single Unified Navigation:** สถาปัตยกรรมการแสดงผลแถบนำทาง (Navbar) รวมศูนย์ไว้ที่ `layouts/navigation.blade.php` เพียงที่เดียว พร้อมแสดงผลวันที่ตามเขตเวลาไทย (`{{ now()->locale('th')->translatedFormat('d F Y') }}`) โดยยกเลิกการใช้ React `<AuthenticatedLayout>` ซ้ำซ้อน เพื่อป้องกันปัญหาเมนูด้านบนแสดงซ้อนกัน 2 ชั้น พร้อมกำหนดคลาส `whitespace-nowrap` บนทุกลิงก์เมนูเพื่อป้องกันข้อความตัดบรรทัดเมื่อหน้าจอมีขนาดก้ำกึ่ง
- **Tailwind Directional Border Conflict Prevention:** มาตรฐานการเขียนคลาส Tailwind CSS สำหรับการ์ดที่มีแถบสีด้านบน โดยต้องใช้คลาสสีแบบระบุทิศทาง เช่น `border-t-4 border-t-emerald-500` ร่วมกับ `border-x border-b border-slate-200` แทนการใช้ `border-emerald-500` (รอบด้าน) เพื่อไม่ให้ชนกับ `border-slate-200` และป้องกันการเกิดคำเตือน `tailwindcss(cssConflict)` ใน VS Code ทำให้ Problems เป็น 0 เสมอ
- **SLA Overdue Warning Alert:** ระบบตั้งเวลาและตรวจจับเคสที่ใกล้หมดเวลา SLA (Warning) และเคสที่เกินกำหนดเวลา (Breached) แบบอัตโนมัติผ่าน Artisan Command `sla:check-warnings` และ Laravel Scheduler ทุก 1 นาที พร้อมส่งแจ้งเตือนทาง Email, Database Notification และบันทึก Log แจ้งเตือนไปยัง LINE เพื่อแจ้งเตือนช่างผู้รับผิดชอบ ทีมเฉพาะทาง Helpdesk และ Manager อย่างทันท่วงที โดยมีฟิลด์ `sla_warning_sent_at` และ `sla_breached_sent_at` ป้องกันการแจ้งเตือนซ้ำซ้อน
- **Audio Notification System (ระบบเสียงแจ้งเตือนสังเคราะห์):** ระบบสร้างเสียงแจ้งเตือนผ่าน Web Audio API โดยสังเคราะห์คลื่นเสียงความถี่โดยตรงจากเบราว์เซอร์อย่างคมชัดและมีความน่าเชื่อถือสูง ไม่ต้องพึ่งพาไฟล์เสียงภายนอก เปิดใช้งานเป็นค่าเริ่มต้น (Default Enabled) ให้กับผู้ใช้งานทุก Role พร้อมปุ่มไอคอนขนาดกะทัดรัด (Compact Icon Toggle) บนแถบนำทาง (Navbar) และบันทึกสถานะผ่าน `localStorage`
- **Sound Tone Selector (ตัวเลือกโทนเสียงแจ้งเตือน):** ฟังก์ชันเลือกโทนเสียงแจ้งเตือนแบบดรอปดาวน์บน Navbar รองรับ 5 รูปแบบเสียงคุณภาพสตูดิโอที่ออกแบบความถี่และความดังให้เหมาะสมกับสภาพแวดล้อมการทำงาน ได้แก่ (1) กระดิ่งกังวาน 3 โน้ต (Chime - ค่าเริ่มต้น), (2) ท่วงทำนองดนตรี 4 โน้ต (Melody), (3) กระดิ่งเคาน์เตอร์ Service Desk (Desk Bell), (4) สัญญาณเรดาร์เตือน (Radar), และ (5) คลาสสิก ดิ่ง-ด่อง (Classic) พร้อมปุ่มกดทดลองฟังเสียงตัวอย่าง (Tone Preview) และจำค่าใน `localStorage` (`itdesk_sound_tone`)
- **Tier 2 Task 2 Authorization (การจำกัดสิทธิ์เริ่ม Task 2):** ข้อกำหนดความปลอดภัยที่อนุญาตให้เฉพาะช่างเทคนิคเฉพาะทางระดับ Tier 2 (`team_hardware`, `team_network`, `team_software`) ของทีมที่ได้รับมอบหมายเท่านั้น ที่มีสิทธิ์มองเห็นและกดเริ่มมาตรการป้องกันปัญหา (`start_preventive_measure`) โดย Role อื่น (Helpdesk, Manager, Administrator) จะเห็นเป็นการ์ดสถานะแจ้งว่าส่งต่องานแล้ว เพื่อความเป็นระเบียบในกระบวนการทำงาน
- **User Dashboard PCAR Isolation (การซ่อนสถานะ PCAR บนแดชบอร์ดผู้ใช้):** นโยบายการแยกบริบทข้อมูลโดยไม่แสดงป้ายสถานะ PCAR (`c.task2_status_label`) หรือหมายเลข PCAR บนหน้าจอ Dashboard และหน้ารายละเอียดใบงานของผู้ใช้งานทั่วไป (Role `user`) เนื่องจาก PCAR เป็นกระบวนการและแบบฟอร์มควบคุมคุณภาพภายในของฝ่าย IT จึงช่วยให้หน้าจอของผู้ใช้งานมีความเรียบง่ายและไม่สับสน
- **SLA Business Hours Calculation (การคำนวณ SLA ตามเวลาทำการ 8x5 และการทบเวลา):** ระบบคำนวณระยะเวลากำหนดส่งมอบ SLA สำหรับบริษัทที่ใช้โหมดเวลาทำการ 8x5 (เช่น บจก. โพลีเมต) โดยนับเฉพาะช่วงเวลา 08:00 - 12:00 และ 13:00 - 17:00 วันจันทร์ถึงศุกร์ (วันละ 8 ชม.) โดยเว้นช่วงพักเที่ยง, เวลากลางคืนนอกเวลาทำการ, วันเสาร์-อาทิตย์ และวันหยุดนักขัตฤกษ์ในระบบ หากเปิดเคสใกล้หมดเวลาทำการ (เช่น เปิดเวลา 16:03 น.) เวลามาตรฐาน 4 ชม. จะถูกใช้ไป 57 นาที และทบเวลาที่เหลืออีก 3 ชม. 3 นาทีไปเริ่มนับต่อในเช้าวันทำการถัดไปเวลา 08:00 น. ส่งผลให้กำหนดครบ SLA คือ 11:03 น. ของวันทำการถัดไป
- **Wall-clock SLA Countdown:** ตัวนับเวลาถอยหลังบนหน้าเว็บ (`Tickets/Show.jsx`) ทำงานโดยคำนวณผลต่างระหว่างเวลาปัจจุบันกับกำหนดส่งมอบ SLA (`sla_due_at`) ตามเวลาจริง (Wall-clock Time) จึงทำให้การเปิดดูเคสนอกเวลาทำการในเวลากลางคืน แสดงผลเวลารวมที่ครอบคลุมถึงช่วงค่ำคืน (เช่น แสดงเหลือ ~15-16 ชั่วโมง) จนกว่าจะถึงกำหนดเวลา 11:03 น. ในเช้าวันทำการถัดไป
- **User Timeline Privacy (การปกปิดชื่อเจ้าหน้าที่บนไทม์ไลน์ผู้ใช้):** นโยบายการแสดงผลเพื่อความเป็นส่วนตัวของทีมงาน โดยในมุมมองของผู้ใช้งานทั่วไป (Role `user`) บนหน้าติดตามสถานะใบงาน ระบบจะไม่แสดงชื่อจริงของเจ้าหน้าที่ผู้ปฏิบัติงานในแต่ละขั้นตอน แต่จะแสดงเป็นข้อความระบุบทบาทกลาง (เช่น "เจ้าหน้าที่รับเรื่อง", "ทีมงานไอที") ในขณะที่ทีมงาน IT และ Administrator ยังคงเห็นชื่อผู้ปฏิบัติงานจริงครบถ้วนเพื่อการตรวจสอบย้อนหลัง (Audit Traceability)
- **Technician Workload Tracking (การติดตามภาระงานของทีมช่างแบบไดนามิก):** วิดเจ็ตบน IT Staff Dashboard สำหรับผู้จัดการ (Tier 3: Role `manager`) และ Administrator โดยสำหรับหัวหน้าทีมระบบจะดึงเฉพาะช่างในทีมที่ตนเองกำกับดูแล (`$user->managedTeams()`) ผ่านความสัมพันธ์ `team_user` เพื่อติดตามว่าช่างแต่ละคนถืองานค้างอยู่กี่ใบ (Analyzing / In Progress), งานที่ส่งมอบแล้วในวันนี้ (Resolved Today), สถานะ SLA ปัจจุบัน, และปุ่มลัด 1-Click Filter เพื่อกรองดูเคสของช่างคนนั้นทันที
- **Helpdesk Normal Users Management (การให้สิทธิ์ Helpdesk จัดการผู้ใช้ทั่วไป):** การขยายสิทธิ์ของ Helpdesk (Tier 1) ให้สามารถเข้าถึงเมนูจัดการผู้ใช้งานทั่วไป (Normal Users) เพื่อเพิ่ม แก้ไขข้อมูล สังกัดแผนก/บริษัท และระงับบัญชีผู้ใช้งานทั่วไปได้ เพื่อความคล่องตัวในการบริการหน้างาน โดยระบบป้องกันไม่ให้ Helpdesk ยกระดับสิทธิ์เป็น Administrator
- **Dynamic Teams & Team Memberships (`teams`, `team_user`):** ระบบบริหารจัดการทีมงานและสายการบังคับบัญชาแบบไดนามิก (Dynamic Organizational Structure) ช่วยให้ Administrator สามารถสร้างทีมใหม่ (เช่น ทีม Hardware, Network, Software, Security), กำหนดหัวหน้าทีม (`manager_id`), และเพิ่ม/ลดสมาชิกช่างในทีม (`team_user`) ได้อิสระผ่าน UI แทนการ Hardcode บทบาทเดิม
- **Team Code Constraint (การจำกัดความยาวรหัสย่อทีม):** กำหนดให้รหัสย่อทีม (Code) มีความยาวไม่เกิน 5 ตัวอักษร (เช่น `HW`, `NET`, `SW`, `SYS`, `SEC`, `QA`) เพื่อความกระชับ ความเป็นระเบียบ และการแสดงผลที่สวยงามลงตัวบน UI ทุกขนาดหน้าจอ
- **Dynamic Sortable Table Headers (การจัดเรียงข้อมูลหัวตารางแบบโต้ตอบ):** ระบบคอมโพเนนต์ `SortableHeader.jsx` ที่อนุญาตให้ผู้ใช้คลิกหัวคอลัมน์ของตารางข้อมูลเพื่อเรียงลำดับ Ascending / Descending ได้ทันที พร้อมไอคอนลูกศรทิศทางกำกับ, Sublabel สองภาษา, Accessibility `aria-sort`, และรองรับแถบจัดเรียงบนอุปกรณ์มือถือ (Mobile Sort Bar) โดยระบบคงค่าการจัดเรียงไว้ใน Query Parameters ใน URL ตลอดการเปลี่ยนหน้าและค้นหา
- **Server-side Business Logic Sorting:** ระบบจัดเรียงข้อมูลอัจฉริยะฝั่ง Server ใน `DashboardController.php`, `TeamController.php`, และ `UserController.php` โดยรองรับทั้งการเรียงลำดับตามตัวอักษร วันเวลา และตาม Business Context เช่น ความเร่งด่วน (Urgent > High > Medium > Low) และสถานะวงจรชีวิตของใบงาน พร้อม Tie-breaker `id desc` ป้องกันข้อมูลกระโดดข้ามหน้า
- **Admin Navigation Grouping (การจัดกลุ่มเมนูตั้งค่าระบบตามภาระหน้าที่):** รูปแบบการจัดกลุ่มภายในเมนูดรอปดาวน์ "ตั้งค่าระบบ (Admin)" โดยแบ่งออกเป็น 2 หมวดหมู่อย่างชัดเจน ได้แก่ "บริการและองค์กร (Service)" (สำหรับจัดการบริษัท, ทีมงาน, หมวดหมู่ปัญหา, วันหยุด) และ "ระบบและความปลอดภัย (System)" (สำหรับประวัติการใช้งาน, ตั้งค่าระบบ, และสำรองข้อมูล) พร้อมไอคอน SVG และป้ายกำกับ เพื่อลด Cognitive Load ตามหลัก Information Architecture (IA) สากล
- **Corporate Branding Settings (การตั้งค่าอัตลักษณ์ระบบ):** การปรับแต่งตราสัญลักษณ์และข้อมูลทั่วไปของระบบในหน้า System Settings ได้แก่ ชื่อระบบ (`app_name`), ข้อมูลติดต่อฝ่ายบริการ (`support_contact`), การอัปโหลดโลโก้ส่วนหัว, โลโก้หน้าเข้าสู่ระบบ และ Favicon โดยระบบได้ตัดฟังก์ชันการตั้งค่าชื่อบริษัท (`company_name`) และสีธีมหลัก (`brand_primary_color`) ออกเพื่อรักษาความสวยงามของโทนสี Indigo/Slate มาตรฐานและป้องกันความซ้ำซ้อนกับตารางบริษัท (`companies`) ของพนักงาน
- **Settings UI Categorization & Sticky Action Bar (การจัดหมวดหมู่หน้าตั้งค่าระบบ):** การปรับปรุงหน้า System Settings ให้จัดหมวดหมู่การตั้งค่าเป็น 3 การ์ดหลัก ได้แก่ "การตั้งค่าแบรนด์และภาพลักษณ์ (Corporate Branding)", "การเชื่อมต่อระบบภายนอก (External Integrations)", และ "นโยบายระบบและความปลอดภัย (System Policies)" พร้อมแถบเครื่องมือบันทึกแบบติดตรึงด้านล่าง (Sticky Action Bar) เพื่อความสะดวกในการใช้งาน
- **Settings Audit Log Delta Tracking (การบันทึกประวัติเฉพาะส่วนที่เปลี่ยนแปลง):** กลไกการตรวจจับความเปลี่ยนแปลงของการตั้งค่าระบบใน Middleware โดยจะเปรียบเทียบค่าคอนฟิกเดิมกับค่าใหม่ และบันทึกลงในตาราง `AUDIT_LOGS` เฉพาะฟิลด์ที่มีการแก้ไขจริงเท่านั้น พร้อมคัดกรองฟิลด์รหัสผ่านว่างเปล่าและคีย์ชั่วคราวออกทั้งหมด
- **Task 2 Inline Edit Extension (การขยายสิทธิ์แก้ไขข้อมูลระหว่างทำ Task 2):** ข้อกำหนดที่อนุญาตให้เจ้าหน้าที่ไอทีทุกระดับ (Helpdesk, ช่างเฉพาะทาง, ผู้จัดการ, Administrator) สามารถแก้ไขข้อมูลการวิเคราะห์สาเหตุ (Why-Why Analysis & Root Cause Detail) และบันทึกการแก้ไขปัญหา (Resolution Notes) ได้ตลอดเวลาในระหว่างที่กำลังดำเนินมาตรการป้องกันปัญหา (Task 2) แม้สถานะหลักของใบงานจะถูกปิดไปแล้ว (`closed`) จนกว่า Task 2 จะเสร็จสิ้นสมบูรณ์ (`done`)
- **Database Engine Diagnostics & Versioning (การตรวจสอบเวอร์ชันและสถานะของฐานข้อมูล):** การตรวจจับและแสดงผลเวอร์ชันของเซิร์ฟเวอร์ฐานข้อมูล MySQL/MariaDB (`PDO::ATTR_SERVER_VERSION`) บนการ์ดสถานะสุขภาพระบบในหน้า System Settings ในรูปแบบ Badge `v{version}` อัตโนมัติ เพื่อให้ผู้ดูแลระบบตรวจสอบสเปกและเวอร์ชันของฐานข้อมูลที่รันอยู่จริงได้ทันทีแบบเรียลไทม์
- **Unified Table Header Alignment (การจัดแนวหัวตารางและข้อมูลมาตรฐานเดียว):** มาตรฐานการออกแบบตารางข้อมูลทั่วทั้งระบบ โดยกำหนดให้หัวตาราง (Table Header) และข้อมูลทุกคอลัมน์ทั่วไปจัดชิดซ้าย (Left-align) เพื่อสร้างเส้นสายตาที่สม่ำเสมอและอ่านง่ายตามหลัก Ergonomics/UI Design ขณะที่คอลัมน์ปุ่มการจัดการ (Actions) จะถูกจัดชิดขวาสุด (`text-right`) เสมอ
- **Deep Slate Console Dark Theme (ธีมมืดคอนโซลสำหรับการ์ดสถานะสุขภาพระบบ):** การปรับปรุงการ์ดแสดงสถานะสุขภาพระบบ 3 รายการ (Cron Scheduler, Database Connection, Storage Health) ในหน้า System Settings ให้เป็นธีมมืด (Dark Theme) สไตล์ Enterprise Monitoring Console โดยใช้พื้นหลัง `bg-slate-900`, เส้นขอบ `border-slate-800`, นีออนไอคอนเรืองแสง และ Dark glow badge เพื่อสร้างความคมชัด น่าเชื่อถือ และแยกออกจากส่วนตั้งค่าแบบฟอร์มทั่วไปอย่างเด่นชัด
- **Two-Line Backup Timestamp Display (การแสดงผลวันเวลาสำรองข้อมูลแบบสองบรรทัด):** การปรับปรุงการแสดงผลวันเวลาที่ทำการสำรองข้อมูลล่าสุดในหน้า Superadmin Dashboard โดยแยกการแสดงผลวันที่ภาษาไทย (`d F Y`) และเวลา (`H:i:s น.`) ออกเป็นสองบรรทัดชัดเจน เพื่อป้องกันปัญหาสายอักขระเวลาถูกตัดทอน (Truncated) และเพิ่มความสวยงาม อ่านค่าง่าย
- **Audit Log Settings Target Nullability (การกำหนด target_id เป็น Null สำหรับการตั้งค่าระดับระบบ):** มาตรฐานการบันทึกประวัติการเปลี่ยนแปลงการตั้งค่าระบบ (`settings.update`) ลงในตาราง `AUDIT_LOGS` โดยกำหนดให้ `target_id = null` พร้อม Type-safe casting เพื่อป้องกันข้อผิดพลาด MySQL 1366 Data Truncation Error
- **Modern Clean Profile Architecture (สถาปัตยกรรมหน้าข้อมูลส่วนตัวแบบโมเดิร์นคลีน):** รูปแบบการออกแบบหน้าจอ `Profile/Edit.jsx` สไตล์พรีเมียมด้วยโครงสร้าง 2 คอลัมน์ที่สมดุล, Hero Header Banner พร้อม Avatar ตราสัญลักษณ์ประจำตัว (Initials), จุดไฟ Active Beacon, ป้ายบอกตำแหน่งและสังกัด, และ Tab Switcher สลับมุมมอง (ทั้งหมด, ข้อมูลส่วนตัว, รหัสผ่าน)
- **Show/Hide Password Visibility Toggle (ปุ่มเปิดปิดการมองเห็นรหัสผ่าน):** ฟังก์ชันไอคอนดวงตาในแบบฟอร์มเปลี่ยนรหัสผ่าน ช่วยให้ผู้ใช้งานสามารถคลิกสลับดูรหัสผ่านที่ตนเองพิมพ์ได้ทันที เพื่อลดความผิดพลาดในการพิมพ์รหัสผ่านใหม่
- **Dynamic Password Criteria Checklist (แถบตรวจสอบเกณฑ์ความปลอดภัยรหัสผ่านแบบเรียลไทม์):** วิดเจ็ตแสดงผลสถานะความปลอดภัยของรหัสผ่านใหม่แบบอินเทอร์แอคทีฟ ตรวจสอบความยาวไม่ต่ำกว่า 8 ตัวอักษร และการยืนยันรหัสผ่านตรงกันแบบเรียลไทม์
- **Administrator Name Immutability Protection (การล็อกชื่อบัญชีผู้ดูแลระบบสูงสุด):** มาตรการรักษาความปลอดภัยในหน้า Profile ที่ล็อกช่อง "ชื่อ-นามสกุล" ของ Role `administrator` ให้เป็น Read-only พร้อมแถบคำเตือนสีส้ม เพื่อรักษาความถูกต้องโปร่งใสของประวัติการทำงาน (Audit Log)
